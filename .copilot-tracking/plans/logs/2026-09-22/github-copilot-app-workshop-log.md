### Plan Deviations from Research

* DR-09: GitHub Pages is not enabled on this repository, recorded during Step 7.3. **Closed 2026-09-22.**
  * Source: Implementation Phase 7, live repository query returning `has_pages: false` and a 404 from the Pages endpoint.
  * Reason: Enabling Pages with the Actions source is an owner action that code cannot perform.
  * Impact: high. The configure step fails on the first workflow run, including pull request runs, because the base path is read on every run rather than hardcoded. That coupling is deliberate; a literal fallback would reintroduce BLD-H1.
  * Closure: Pages was enabled with the Actions source and the site is served at `https://devopsabcs-engineering.github.io/github-copilot-app-workshop/`. Fifteen live URLs were requested and all returned HTTP 200, including both deck downloads, with no href leaking a `/docs/` prefix.

* DR-10: The `ruby/setup-ruby` action is absent from the repository Actions allow-list, recorded during Step 7.3. **Closed 2026-09-22 by observation, and the original diagnosis was wrong.**
  * Source: Implementation Phase 7, live repository query returning `allowed_actions: "selected"` with GitHub-owned actions permitted and no third-party entry for this action.
  * Reason: Allow-list membership is an owner action. The organization-level policy could not be read, returning HTTP 403, so only the repository level is confirmed.
  * Impact: high. The build job cannot provision Ruby until this is resolved. Remediation is recorded in PUBLISHING.md.
  * Closure: the action was already permitted, carrying `verified_allowed: true`, so no allow-list change was ever needed. The 403 on the organization policy meant the gap could not be ruled out, not that it existed. The first run failed for an unrelated reason and is recorded as DD-09.

* DD-09: The `ruby/setup-ruby` pin was moved forward from the starter-workflow SHA, recorded 2026-09-22.
  * Plan specifies: pin every action by the verified commit SHA taken from the GitHub starter workflow.
  * Implementation differs: the pin is v1.325.0 at `e8944e80fb94b20106697132f8c20c665fab29e9`.
  * Rationale: the starter-workflow revision bundled a Ruby build index that predated 3.2.11 and failed outright on the pinned interpreter version. Downgrading Ruby to match a stale index would have desynchronized CI from the locally verified interpreter, so the action pin moved instead. Still a full-length SHA with a tag comment, so DD-04 is unaffected.

* DD-10: The French navigation tree was flattened to top level, recorded 2026-09-22.
  * Plan specifies: nothing. The plan never addressed the shape of the French sidebar relative to the English one.
  * Implementation differs: the six French section entries are now siblings at top level, matching English exactly, rather than children of a `Français` parent.
  * Rationale: the user asked for a language toggle where the sidebar shows only the selected language, modeled on a sibling repository. With French nested one level deeper, the toggle would have moved a reader between structurally dissimilar sidebars, so the feature required the flattening. The French home page is titled `Accueil` rather than `Atelier` because `Atelier` and `Ateliers` differ by one character and would have sat adjacent; the mild asymmetry against `Workshop` is the lesser problem, and it is recorded as ID-03.

* DD-11: The navigation validator's grouping key became language-aware, recorded 2026-09-22.
  * Plan specifies: a navigation check grouping pages by grandparent and parent.
  * Implementation differs: page language is now part of the key.
  * Rationale: flattening French put both trees at the same nesting depth, so the original key merged English and French entries into one group and reported six false collisions. This is a correction rather than a relaxation. Two pages colliding within one language still fail, which was proved by injecting a same-language collision and observing exit 1.

* DD-12: Two validator summary lines were de-verdicted, recorded 2026-09-22.
  * Plan specifies: nothing. This was found while making DD-11.
  * Implementation differs: `validateNavigation` printed `Navigation OK: ... no parent or nav_order conflicts` unconditionally, including on the very run that reported a collision. Both that line and its counterpart now report measured counts and leave the verdict to the exit code.
  * Rationale: a tool that announces its own pass regardless of what it found is the same defect class as the fabricated verification claim caught in Phase 8. Fixing it was in scope on those grounds even though it was outside the requested feature.

* DD-13: A `validateLanguageToggle` check was added, recorded 2026-09-22.
  * Plan specifies: nothing.
  * Implementation differs: every page must declare `lang_ref`, the target must resolve to a real page in the other language, and the mapping must be symmetric.
  * Rationale: the toggle is rendered from front matter that nothing else reads, so a broken or asymmetric `lang_ref` would have been invisible until a reader clicked it. It runs in full mode only, matching `validateCounterparts`, because a subtree validated in isolation cannot see its counterpart.

* DD-14: Published accessibility figures were revised downward after re-measurement, recorded 2026-09-22.
  * Plan specifies: the figures recorded during Phase 8 against the locally built site.
  * Implementation differs: 15,677 passing axe-core checks rather than 16,101, and 56 incomplete contrast nodes rather than 75.
  * Rationale: half the navigation links are now hidden by CSS and axe does not evaluate hidden nodes, so the drop is expected and the verdicts are unchanged at zero violations across 56 runs. The re-measurement was run against the published site rather than a local build. Two statements on the validation status pages had also been falsified by the deployment, including a bullet asserting the site was not published; both were corrected the same day the facts changed.

* DD-15: A `validateRenderedNavigation` check was added, recorded 2026-09-22.
  * Plan specifies: navigation integrity is validated from front matter, and the built site is read only to assert the base path.
  * Implementation differs: the validator now also reads every built HTML document and asserts, per page, that the head hides the other language and not its own, that every sidebar link declares a language so the rule can match it, that no unexpected language appears, and that the toggle link names the other language in both `lang` and `hreflang`.
  * Rationale: the sidebar is emitted once and cached, so the per-page scoping lives entirely in CSS that no source-level check can see. The counts that proved the feature worked came from scripts that were deleted the same day, which is exactly the class of evidence this repository has already been burned by. Four deliberate injections into a built page were each detected with exit 1 and then reverted, so the check is known to be capable of failing rather than assumed to be.

* DR-08: Manual visual render of both decks was not performed, recorded during Step 5.3 and reaffirmed during Step 8.3.
  * Source: Implementation Phase 5, reopened in Implementation Phase 8.
  * Reason: No PowerPoint or equivalent renderer exists in the implementation environment. An intermediate Phase 8 pass recorded this gate as closed on the strength of a render that never happened; the final reconciliation pass reversed that claim. Deck geometry was measured from the generated binaries, one hundred sixty text shapes across thirty-two slides, with no overflow found. Measuring a binary is not looking at a slide.
  * Impact: medium. Blocking for delivery. Slides 03 and 07 carry the longest bodies, slide 14 the longest titles, slide 12 the longest French kicker, and slide 01 the longest French footer.

* DD-08: Navigation language marking is absolute, not relative, recorded during Step 2.3.
  * Research recommends: mark each foreign-language nav link, which reads naturally as marking a link when its language differs from the current page.
  * Plan implements: every nav link declares its own target language unconditionally.
  * Rationale: The theme renders its sidebar through `include_cached`, and the component's own source declares it depends on `site` only. Page-dependent logic inside it silently serves the first-rendered page's answer to every page, which the build confirmed by producing a French sidebar byte-identical to the English one. A redundant `lang="en"` inside `<html lang="en">` is valid and inert; a cache-dependent sidebar is not. Consequence for later work: no override inside the sidebar tree may read `page`.

* DD-07: Validator dependency remediation, recorded during Step 1.1.
  * Research recommends: nothing explicit; the plan named only the deck library and a ZIP reader.
  * Plan implements: `js-yaml` on the 5.x line and an `image-size` override to 2.0.4.
  * Rationale: The first production audit returned three high advisories. One `js-yaml` 4.x advisory has no backported fix, and no pptxgenjs release on either major requests a patched `image-size` range. Remediating rather than accepting keeps the recorded baseline at zero, which is what Step 1.1 requires `validate:all` to enforce. Both are documented with smoke tests in SUPPLY-CHAIN.md. The `image-size` v2 module shape changed, and the smoke test did not cover image embedding because no rehearsal screenshots exist; that caveat is carried against WI-02.

* DD-01: Publishing toolchain version.
  * Research recommends: `github-pages` gem 232, pinning Jekyll 3.10.0, as the safe Pages-fidelity choice.
  * Plan implements: Jekyll 4.3 with direct dependencies.
  * Rationale: The selected publishing path builds through GitHub Actions rather than the managed Pages build, so Pages gem fidelity buys nothing. Jekyll 4 also removes the Jekyll 3 behavior where `exclude` replaces the defaults instead of extending them, which the research flagged as a trap that silently publishes unintended directories. This closes the research owner decision five in favor of Jekyll 4.

* DD-02: Theme delivery mechanism.
  * Research recommends: `remote_theme: just-the-docs/just-the-docs@v0.10.1` with the `jekyll-remote-theme` plugin.
  * Plan implements: the `just-the-docs` gem referenced through `theme:` in the Gemfile and configuration.
  * Rationale: `remote_theme` fetches the theme over the network at build time, adding a failure mode inside CI and inside restricted customer networks. The gem is lockfile-pinned and offline-resolvable. * DD-06: README agenda derivation.
  * Research recommends: nothing explicit; the sibling README is a hand-authored document.

  * Rationale: BLD-H3 names the README as a fifth content surface. A prose instruction to keep titles and durations matching is a hand check that drifts. Machine validation is the only mitigation consistent with the other four surfaces.

* DD-03: Deck output directory posture.
  * Research recommends: `docs/assets/decks/` listed in the target tree.
  * Plan implements: the directory stays gitignored, with the generator creating it recursively and CI generating decks before the Jekyll build.
  * Rationale: Binary build outputs should not be committed, but the research correctly identified that a gitignored directory plus a generator that assumes it exists produces an ENOENT on a clean runner. Creating the directory in the generator resolves the contradiction without committing binaries.

* DD-04: Action version pinning.
  * Research recommends: a specific set of action versions drawn from the official starter workflow.
  * Plan implements: resolving versions against the official starter workflow at implementation time, pinning each to an immutable commit SHA with the tag in a trailing comment, and recording the retrieval URL and date.
  * Rationale: The research itself marks BLD-C2 as unattributable and directs resolution at implementation time. Copying a version list from a planning document would reintroduce the defect. Tag-only pins are mutable, which is the same objection that removed the remote theme fetch, so SHA pinning and retrieval provenance are carried as well.

* DD-05: Validation script language.
  * Research recommends: `scripts/validate-workshop.ps1`.
  * Plan implements: `scripts/validate-content.mjs` and `scripts/validate-decks.mjs` in Node.
  * Rationale: The Node toolchain already exists for deck generation, the Pages runner is Linux, and PowerShell would add a second runtime to CI for no benefit. This also keeps the validators able to import the shared content model directly.

## Implementation Paths Considered

### Selected: Actions-built single artifact with a shared bilingual content model

* Approach: One GitHub Actions workflow installs Node and Ruby, generates both decks from a shared content model, runs parity and deck validators, builds one Jekyll site containing both language trees, and uploads a single Pages artifact.
* Rationale: It is the only path that can run the npm deck generator during publishing, and a single build keeps the English and French navigation, search, and deck downloads in one coherent site. The shared content model plus a real validator is the only mitigation the research identified for four-way content drift.
* Evidence: .copilot-tracking/research/2026-09-22/github-copilot-app-workshop-research.md, Technical Scenarios and Alternatives table, publishing row.

### IP-01: Two separate single-language builds for WCAG language of parts

* Approach: Build an English site and a French site independently, each with a uniform document language, avoiding the mixed-language navigation problem entirely.
* Trade-offs: Removes the need for a navigation override and satisfies WCAG 3.1.2 without Liquid changes. Costs a second build pipeline, splits search, breaks cross-language switching, doubles deployment surface, and makes the downloads page harder to keep paired.
* Rejection rationale: The navigation override in Step 2.3 is a bounded change to one include file, and it preserves a single site with working cross-language navigation. This closes research owner decision six in favor of the override. Revisit only if the pinned theme version makes the override unmaintainable.

### IP-02: Publish from a branch `/docs` folder

* Approach: Use the managed GitHub Pages branch build instead of Actions.
* Trade-offs: Simplest possible setup with no workflow to maintain, and it survives an organization policy that blocks Actions.
* Rejection rationale: The managed build cannot run the npm deck generator, so the decks would have to be committed as binaries and could drift from the content model without any check. The research rejected this path for the same reason. Because DD-01 also removes the `github-pages` gem, the selected path has no fallback; Step 7.3 requires that this single point of failure be either accepted in writing or covered by a documented fallback with its plugin delta stated. This path is independent of OD-01 and IP-03, which concern the deck library version rather than the publishing mechanism; choosing IP-02 would make IP-03 moot by removing deck generation from the build entirely.

### IP-03: Pin pptxgenjs 3.x instead of 4.0.1

* Approach: Use the previous major version, which does not pull the `https` placeholder package as a transitive dependency.
* Trade-offs: Avoids a questionable supply-chain entry in a customer-facing repository. Loses whatever v4 improvements exist, and the research verified that the APIs this plan uses are unchanged between the majors, so the functional cost is near zero. Against that, v4.0.1 is the current release while 3.x is older and less likely to receive fixes.
* Rejection rationale: Not rejected. This remains an open owner decision, recorded below, and must be settled before Step 1.1 installs a version. The research verified that `addSlide`, `addText`, `addNotes`, `writeFile`, and `lang` behave identically across both, so either choice is implementable without redesign.

## Open Owner Decisions

These carry forward from the research and cannot be closed by planning. Two block implementation steps; the rest are delivery-operational. Entries are grouped by topic rather than strict numeric order.

* OD-01 (blocks Step 1.1): Is the `https` transitive package acceptable in a customer-facing supply chain, or should the deck library be pinned to its previous major version, which does not pull it? Alternative recorded as IP-03. Recommendation: pin the previous major for customer-facing delivery, since the research verified that every API this plan uses behaves identically across both majors.
* OD-06 (blocks Implementation Phase 2): Which Just the Docs version is pinned? Recommendation: pin the current release rather than the v0.10.1 the research inspected, because it carries the WCAG contrast fixes that matter for a public-sector audience, and accept that Steps 2.2 and 2.3 must copy their overrides from the installed gem rather than from the research record. Choosing v0.10.1 instead keeps the verified internals but ships known contrast defects.
* OD-07: Who assigns learners to the beginner or intermediate track at registration, and what mix is expected? The source review rejected a split that is only an extra sentence, so Steps 3.2 and 4.2 make the split structural with per-track acceptance bars and paired seating. The assignment mechanism and the expected mix are delivery-operational and cannot be closed by authoring. Recommendation: assign from the registration form with a self-declared experience question, and pair each intermediate learner with a beginner where the roster allows.
* OD-08 (raised during Step 1.1): Who reviews and accepts the `https` placeholder package for customer-facing delivery? It is an inert placeholder shadowed by Node's built-in module and is unavoidable on either pptxgenjs major, so the remediation if a customer reviewer rejects it outright is a different deck library, which reopens ID-01. The call is needed before Implementation Phase 5 generates decks. Recommendation: accept on the technical grounds recorded in SUPPLY-CHAIN.md, and raise it proactively in any customer supply-chain review rather than waiting to be asked.
* OD-02: Who approves executing AI-generated code on managed devices at each customer, and has the request been made?
* OD-03: Is the hands-on cap negotiable at sixteen, or is twenty fixed, and how many facilitators are available?
* OD-04: Are English and French delivered as separate sessions or one bilingual cohort?
* OD-05: May learners retain generated code, and on which machine?
